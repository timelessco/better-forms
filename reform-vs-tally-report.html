Embed Performance Report

Reform vs Tally

Head-to-head load performance of the two embeddable form widgets, measured on an identical field set (short answer, long answer, multiple choice, checkboxes, multi-select, number, email, phone). Captured with Chrome DevTools traces (cold cache, no throttling) plus direct asset fetches for exact compressed transfer sizes.

📅 2026-05-27 🧪 Chrome DevTools trace · cold cache 📦 Compressed sizes via brotli/gzip fetch 🔬 scenarios: shown · hidden · image · mobile Reform (better-forms-mu.vercel.app) Tally (tally.so)

Bottom line

Reform wins where it counts for an embed: the form appears ~2× faster, uses about half the main-thread time, and ships zero third-party trackers. Tally is ~10% lighter on the wire and makes fewer requests, but pays for it with a slow server response and heavy continuous layout work. Reform leads on nearly every axis — and on real-world mobile (4× CPU · Slow 4G) the lead widens to 6.1× (1.0 s "Good" vs 6.1 s "Poor").

What the numbers mean

The detail behind each headline.

⚡ Speed — Reform wins time-to-visible

Reform paints the form at 188 ms vs Tally's 403 ms. The gap is almost entirely server-side: Reform's TTFB is 23 ms (Vercel edge) while Tally's is 351 ms (origin render).

For an embed — where the visitor stares at a blank iframe until the form appears — this is the metric that matters most, and it's Reform's clearest win.

⚖️ Weight — basically a tie

Compressed first-visit payload: Reform 806 KB vs Tally 729 KB. JS is a wash (622 vs 661 KB). Reform's overage is fonts (124 KB vs 47 KB) — two families, Inter Variable + Timeless Serif — and a larger SSR document (58 KB vs 19 KB).

🧵 Main thread — Reform much lighter

Reform burns 706 ms vs Tally's 1,515 ms. The split is the story: Tally spends 914 ms in style/layout recalc (vs Reform's 109 ms) — continuous re-layout from auto-height + animations. Reform does more scripting but far less layout, so it settles faster on low-end devices.

🔌 Request shape

Reform code-splits aggressively — ~53 tiny chunks, one per field type, lazy-loaded. Tally ships fewer, fatter Next.js vendor chunks. Both are fine over HTTP/2; Reform's network stays active longer (lazy chunks trickling in) but the form is interactive at ~190 ms regardless.

🛡️ Privacy / third parties — Reform cleaner

On load Tally fires 3 Sentry POSTs, Plausible analytics, and a tally.so events beacon. Reform calls only its own first-party analytics + one server function — no external trackers, smaller privacy surface, less for ad-blockers to trip on.

🎯 Interactivity & stability — both excellent

INP is 3–4 ms for both (instant response to taps) and CLS is ~0.00 (no layout jank). Neither widget has an interactivity or visual-stability problem — the meaningful differences are all in load speed and CPU.

Why Reform's TTFB wins: caching, not geography

It's tempting to assume Tally is slow because it's served from a far region. Measured from Mumbai (with CDN + region headers), that's not it — both serve from Indian edges. The real difference is the caching strategy.

TTFB — what a visitor actually gets

Measured from Mumbai. Reform is bimodal (cached vs cold); Tally is constant. Lower = faster.

It's the cache, not the map

Both sit one short hop from an Indian edge — Reform on Vercel bom1 (Mumbai), Tally on Cloudflare MAA (Chennai) — with near-identical connect latency (6–46 ms). Distance isn't the story.

Reform serves the form page from the regional edge cache (x-vercel-cache: HIT) → repeat visitors anywhere get ~87 ms, no matter where the origin runs. Tally sets no-store / cf-cache-status: DYNAMIC → it re-renders every request, so every visitor everywhere pays ~390 ms, even on repeat views.

Honest nuance: Reform's cold render (first visit in a region, or right after a content update purges the cache) is ~1.3 s — actually slower per-request than Tally's 390 ms. Reform wins delivered TTFB by caching aggressively, not by a faster server. Cold misses are the exception, not the rule.

🔑 Takeaway

Half-right: yes, Reform's regional edge cache means origin location barely matters for cached hits (~87 ms anywhere). But it's a caching-strategy win, not a geography win — Tally is just as close (Chennai edge); it simply refuses to cache (no-store) and re-renders on every request. The one place location still bites is a cold miss — the first visitor in a region, or the first hit right after a content update invalidates the cache — where Reform pays a ~1.3 s origin render before the edge is warm again.

Why they react differently

The title sits on Reform's critical paint path, but not Tally's.

Reform: LCP rises 188 → 261 ms. The large serif title was the LCP element and painted instantly on the fallback font; hide it and the "largest paint" falls to a later-rendering field block (render delay 165 → 236 ms). FCP still fires fast at 152 ms. Upside: the 22 KB Timeless-Serif font is no longer downloaded — it's only fetched when a title actually renders.

Tally: LCP essentially flat (403 → 422 ms) and transfer unchanged (doc 19.4 → 19.5 KB). Tally is server-bound — TTFB alone is ~360 ms — so the title was never the bottleneck, and its font/assets load regardless.

Why the image hurts one and not the other

Same idea, very different image pipelines.

Tally: LCP jumps 422 → 561 ms (+139). Its banner is a 123 KB, 1080px JPEG served straight from Unsplash — Chrome's Image Delivery audit flags it as ~100 KB wasted, ~50 ms recoverable (no resize, no WebP/AVIF). It's the LCP element and took 112 ms to load, on top of a 340 ms server TTFB.

Reform: LCP stays low at 215 ms — no penalty. The banner is requested right-sized (76 KB, w=800) via the image CDN, the avatar is a vector sprite (≈0 bytes), and the 26 ms edge TTFB leaves headroom. Chrome raises no image-delivery issue.

🔑 Takeaway

Adding a header image is where the two diverge most. Tally pays +139 ms LCP for an unoptimized 123 KB banner that Chrome explicitly flags. Reform absorbs the same feature with no LCP penalty (215 ms) by requesting a right-sized image and using a vector avatar — landing ~2.6× faster than Tally with images (215 vs 561 ms). Total transfer converges (~860 KB each), but Reform spends those bytes on JS+fonts while Tally spends them on an oversized JPEG on the critical path.

Scenario: real-world mobile (4× CPU · Slow 4G)

The one that matters most — most forms are opened on a phone. Mid-tier device emulation (412×915, 4× CPU slowdown, Slow 4G network), as-shipped form with banner + avatar. This is where the desktop numbers stop telling the whole story.

LCP — desktop vs real-world mobile

Why mobile blows the gap wide open

Throttling exposes what fast hardware hides.

Tally: LCP collapses to 6.1 s — its 123 KB banner alone takes 5.5 s to download on Slow 4G, and it's the LCP element. Chrome flags both Image Delivery and Forced Reflow. At 6.1 s this is squarely in Google's "Poor" Core Web Vitals band (> 4 s).

Reform: LCP holds at 1.0 s — a "Good" score (< 2.5 s). The right-sized banner + vector avatar aren't the bottleneck; LCP is gated by JS hydration on the throttled CPU, and the 27 ms edge TTFB keeps the start fast. 6.1× faster than Tally on mobile (vs 2.6× on desktop).

🔑 Takeaway

On a real phone and network, the desktop "2.6×" becomes 6.1×. Reform stays in the Good LCP band (1.0 s) while Tally falls to Poor (6.1 s) — a form a real visitor would likely abandon before it paints. The culprit is Tally's unoptimized banner on a slow link; Reform's edge TTFB + right-sized assets keep it fast where it counts.

Final verdict

Across every scenario — bare form, hidden title, header image, and especially real-world mobile — Reform is the faster, lighter-on-the-CPU, more privacy-respecting embed. The lead widens exactly where it matters most: a throttled phone on a slow network, where Reform paints in 1.0 s (Good) and Tally in 6.1 s (Poor).

Method: Chrome DevTools performance traces with cache disabled (ignoreCache reload) on a local machine. Desktop scenarios are unthrottled; the mobile scenario adds 4× CPU slowdown + Slow 4G + a 412×915 mobile viewport. LCP/TTFB measured by navigating to each form app directly as a top-level page; CPU and request counts from the embed pages (demo.html / demo-tally.html); compressed transfer sizes measured by fetching every asset directly with brotli/gzip (the cross-origin iframe hides wire sizes from the trace); image sizes from the Resource Timing API.

Caveat: single cold run per scenario — absolute milliseconds vary run-to-run, but the gaps (TTFB, layout time, font weight, third-party calls, mobile image load) are architectural and reproducible. The mobile run confirms empirically that throttling widens Reform's lead (2.6× → 6.1×), rather than leaving it hypothetical.
